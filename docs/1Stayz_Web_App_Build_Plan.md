## Work packages, in order

Each package is a PR to `main`. Run `npm run lint && npm run typecheck && npm run build` and the database checks (`DATABASE_URL=… supabase/tests/run.sh`) before each push; CI runs both on every PR. Then tick the package off in the status table at the bottom, **and add the package's setup steps (accounts, keys, env vars, dashboard settings, migrations) to `claude/1Stayz_Your_Setup_Checklist.md`**, the per-environment checklist the user reviews. Copy any changed project docs into the web-app repo's `docs/` folder in the same PR (added in #19; the project copies are the source of truth). After the merge, apply new migrations to the **dev** Supabase project (`xuigrinujnmtwtznhkgk`) through the Supabase connector, one transaction per migration with its `supabase_migrations.schema_migrations` row under the file's version, then check the schema and security advisors and report it in chat. Never touch staging, prod or the marketing project; the user pushes those with the CLI.

### WP-0 · CI in all three repos (OPS-01, DB-02)
- Add `.github/workflows/ci.yml` running lint, typecheck and build on every PR and every push to `main`.
- In 1stayz-web-app, add an RLS coverage check that fails when any `public` table lacks RLS or a policy.
- The SQL tests need Postgres. Use a `supabase start` job or a postgres service with `supabase/tests/supabase_stubs.sql`.

**Done when:** CI is green on each repo, and a test migration without RLS makes it fail.

### WP-1 · Threads, messages, audit (DB-01 rest, DB-04)

**Tables:**
- `church_threads`: one per visit. Holds channel, status (open, closed, opted_out), `twilio_conversation_sid`, `email_thread_key`, `service_end_at` and `first_contact_due_at`.
- `church_thread_participants`
- `church_messages`: direction, sender (guest, assistant or staff), body, channel, provider ids, `email_message_id`, `in_reply_to`, `data_class`, status (draft, held, approved, sent, failed, received), `sent_at`.
- `church_audit_log`: append-only. Records message events and model calls with model, guardrail version, Tier-2 decision, tokens and latency.

**Rules:**
- Follow the `church_people` pattern: `church_id` on every row, composite FKs `(church_id, …)`, forced RLS through `is_church_member()`, and the app never writes `church_id` from the browser.
- Webhooks and the scheduler write through a server role or security-definer functions only.

**Done when:**
- Migrations apply cleanly.
- SQL tests prove another church's rows return 0 (ISO-1).
- SQL tests prove an unauthenticated caller gets nothing (ISO-3).

### WP-2 · Intake `/api/intake` (UI-02; feeds SS-03)
- Authenticate with a shared secret per church.
- Behaviour:
  1. Upsert the person.
  2. Create the visit, idempotent on `(church_id, source, source_event_id)`.
  3. Create the thread with `service_end_at`, taken from `church_services` and `churches.timezone`.
  4. Set `first_contact_due_at` to `service_end_at` + 30 minutes. *(Since WP-1 the database sets this by trigger; intake only sets `service_end_at`.)*
- Normalize names (trim and case). Never auto-merge on phone alone: set `needs_review` instead (guidelines 4.8.3).
- Server writes need the service-role key (server-only env var, e.g. `SUPABASE_SERVICE_ROLE_KEY`), used only in route handlers / server code, never in the browser.

**Done when:**
- A duplicate post creates nothing new.
- Name variants resolve to one person.
- A guest who submits during the service still gets a deadline of service end + 30 minutes.

### WP-3 · Twilio Conversations + inbound routing (UI-03, UI-04)
- Use Twilio Conversations, one conversation per visit, with the guest as the SMS participant. Store the SID on the thread.
- Route inbound messages by the open conversation for the (to, from) pair. Do not add a separate raw incoming-SMS webhook.
- Port the signature check from `1stayz-landing-page/lib/twilio.js`. Don't call that code: it is marketing-only.
- Use a separate guest number and 10DLC campaign from the marketing one.

**Done when:** in the sandbox, two replies from a guest land on the same thread.

### WP-4 · Consent, STOP/HELP, quiet hours, scheduler (UI-06, UI-06a, DB-05)
- STOP closes the thread, writes `church_consents` and blocks every send.
- HELP returns the configured text and leaves the thread open.
- Quiet hours run 9 pm–8 am in the guest's local time. A deferral must never silently push first contact past its deadline: alert instead.
- The scheduler runs on Vercel cron or a Supabase scheduled function. It sends at the earlier of "template ready" or "deadline − 5 minutes".
- Log `sent_at − service_end_at` for each visit.
- Block go-live for a church with no service schedule.

**Done when:**
- STOP and HELP tests pass.
- At least 95% of test visits get first contact within 30 minutes.
- Opt-out survives a restart.

### WP-5 · Email (UI-05)
- Send first contact by email when the guest prefers email or has no phone. Email is also the fallback if 10DLC is late.
- Store the outgoing `Message-ID`.
- Match replies by `In-Reply-To`/`References`, then fall back to the subject.
- Use a mail subdomain separate from marketing.

**Done when:** an email reply lands on the same thread as the SMS.

### WP-6 · Real inbox, escalation queue, Today page, Shadow approval (UI-07, UI-08, UI-09)
- Replace the mock imports in `ConversationsPage`, `TodayPage` and the Person page's conversation panel with Supabase reads.
- Staff can reply in the thread.
- In Shadow mode, each outbound message is `held` until a staff member approves it. Record the approval delay.
- The leader list shows replied, needs follow-up, coming back and at risk.

**Done when:** the Demo 2 flow runs end to end on staging: intake, first contact within 30 minutes, SMS and email on one thread, and STOP closes it.

### WP-7a · AI groundwork (AI-01 rest, AI-03, AI-06)
- Add `classify()` to `src/lib/ai`, plus a unit test against the stub.
- Data-class tagger (C1–C6), with rules first and Tier-1 second. It errs toward the stricter class.
- Guardrail config loader with versioning: the version is written to every model-call audit row.

### WP-7b · Reply agent + evals (AI-04, AI-05, AI-07, AI-08, AI-09)
- Working context is the last 8 turns, a fact card and the guardrails. Assert `church_id` on every item (ISO-2).
- First-contact generator.
- Reply agent: one question per message, SMS length cap, and a Tier-2 gate.
- Escalation classifier.
- A 40-conversation eval set: at least 90% pass, and 100% on must-route-to-human cases.
- Use only synthetic guest data until the AI-02 Groq retention terms are confirmed.

### WP-8 · Go-live hardening (DB-07, DB-09, DB-10, UI-09)
- Mask C1/C3 in logs (Sentry scrubbing).
- Alert the PM within 5 minutes of a failed send.
- Per-church daily token budget.
- Write the runbook.
- Verify backups.

### WP-9 · Real data on every page (after go-live scope; added 2 Nov)
- No church ever sees the demo's sample data: pages still built on samples show "coming soon" outside the demo workspace.
- Dashboard, Insights (pilot metrics by week, CSV) and AI Training (approved guardrails, versions, assistant status, last 7 days) read the church's own rows.
- Follow-Up Engine and Appointments stay "coming soon" (outside the pilot scope).
